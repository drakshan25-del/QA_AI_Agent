# Chapter 2 — Background and Critical Literature Review

## 2.1 Large language models for test generation

The feasibility of generating tests with LLMs was established early for unit testing. Schäfer et al. (2024) evaluated their TestPilot approach across 25 npm packages and 1,684 functions, prompting models with function signatures, implementations and documentation examples, and repairing failed generations by re-prompting with the error message. Their strongest configuration achieved a median statement coverage of 70.2 %, but the study's most instructive result for the present project is methodological: a substantial fraction of raw generations failed to run at all, and usable coverage was obtained only because the pipeline *around* the model validated outputs and fed failures back. The re-prompt-with-error loop that this project implemented for automation generation (Section 5.3) is a direct descendant of that finding, generalised from unit tests to browser automation.

Kang, Yoon and Yoo (2023) approached generation from a different artefact — natural-language bug reports — and showed with LIBRO that an LLM could reproduce roughly one third of Defects4J bugs as executable tests. Two aspects of their design were influential here: generated tests were subjected to post-processing and validity checks before being shown to developers, and the framework ranked outputs rather than trusting them. Both studies, however, target Java or JavaScript unit tests, where the execution context is a compiler and a test runner. Web user-interface testing adds a failure mode neither study confronts: a test can compile, run and still be wrong because the element it addresses does not exist.

That failure mode is quantified by Li et al. (2026), who evaluated eleven LLMs on generating value-filling tests for 146 web forms across thirty open-source Java applications, using a "successfully submitted rate" as the effectiveness measure. Performance varied sharply across models — non-GPT-4 models fell short of GPT-4 by margins of 9 to 74 percentage points — and the study demonstrates that even the strongest general models are unreliable at grounding actions in a concrete page. Their measurement is end-to-end submission success; what it does not provide is an *architecture* for closing the gap. The present project's response — distilling the live page into an inventory and rejecting, at generation time, any locator or action that the inventory cannot support — treats Li et al.'s finding not as a model-selection problem but as an evidence-grounding problem.

## 2.2 API testing with language models

For API testing, Kim et al. (2024) proposed RESTGPT, which mines machine-interpretable constraints and example values from the natural-language portions of REST API specifications, reporting better rule extraction and value generation than prior specification-analysis techniques. Their premise — that the specification, not the model's memory, should be the authority on what the API accepts — is shared by this project, but the two designs draw the boundary differently. RESTGPT uses the LLM to *enrich* the specification for downstream testing tools; the pipeline built here uses the specification to *police* the LLM: every generated client call is checked against the parsed OpenAPI surface, and requests to undocumented endpoints are rejected and regenerated (Section 5.2). The distinction matters when the model is small and local — a 7B model's knowledge of any particular API is negligible, so enrichment without enforcement would leave hallucinated endpoints undetected until execution.

## 2.3 Agentic software engineering

A parallel line of work gives the model an agency loop rather than a single prompt. Yang et al. (2024) showed with SWE-agent that a carefully designed agent-computer interface — compact file viewing, guarded editing, immediate linting feedback — raised autonomous repository-level task performance to 12.5 % pass@1 on SWE-bench, arguing that interface design, not raw model capability, was the binding constraint. Bouzenia, Devanbu and Pradel (2025) demonstrated with RepairAgent that an autonomous agent interleaving information gathering, fix generation and validation could repair 164 Defects4J bugs, including 39 not fixed by prior techniques. Both systems validate a central premise of this project — that models become useful when embedded in tool loops with deterministic feedback — while differing from it on the question of authority. SWE-agent and RepairAgent are autonomous within their episode: the agent decides, acts and self-validates. The system built here deliberately withholds that autonomy at every irreversible boundary, requiring versioned human approval before execution, commit or dispatch, because in a quality-assurance context the generated artefact *is* the safety mechanism for someone else's software; an agent that validates its own tests occupies both sides of the assurance relationship. The literature offers little guidance on such governance structures, and their design and cost are part of this project's contribution.

## 2.4 Trusting generated code

The security dimension of generated tests is examined by Zhang et al. (2026), who studied whether ChatGPT could produce security tests demonstrating exploitable vulnerable dependencies, obtaining generated tests for all 55 studied applications and successful attack demonstrations for 24. Read constructively, the study shows LLMs can exercise security-relevant behaviour; read adversarially, it shows that generated code is capable of mounting real attacks — which is precisely why the present system treats its own generator as a potential adversary. The deterministic gate described in Section 5.4 blocks process execution, network primitives, dynamic code, reflection and filesystem mutation in generated files, resolves aliased imports before matching, and orders pytest collection after static analysis specifically because collection executes module-level code. To the author's knowledge the reviewed literature contains no comparably explicit threat model for the *test generator itself*; TestPilot and LIBRO validate that generated tests work, not that they are safe to run.

## 2.5 Software evolution and regression

Regression is where AI-generated suites will live or die in continuous delivery, and it is the least mature area of the reviewed literature. Haroon, Khan and Gulzar (2026), in a mutation-driven preprint spanning 22,374 program variants and eight LLMs, report that LLM-generated tests behave inconsistently as programs evolve — pass rates degrade under semantics-altering change in ways that are difficult to predict — which challenges any workflow that regenerates tests wholesale on each release. The design position taken here is complementary rather than contradictory: generated suites are frozen once approved, executions are compared run-over-run by per-test outcome transitions, and a pass-to-fail transition against a promoted baseline — not the model's opinion — is the regression signal that gates the pipeline (Sections 4.8, 5.6). Because the source is a preprint, its findings are treated as indicative rather than settled.

## 2.6 Local models, fine-tuning and evaluation practice

Requirement documents are commercially sensitive, which motivated local inference. The Qwen2.5 family (Qwen Team, 2024), with its code-specialised variant (Hui et al., 2024), represented the strongest openly available models runnable on a 16 GB workstation at the time of the project, and DeepSeek-R1 (Guo et al., 2025) offered a reasoning-trained alternative whose long deliberation traces trade latency for accuracy — a trade-off that Chapter 7 shows to be decisive in this workload. Adapting such models cheaply is enabled by low-rank adaptation (Hu et al., 2022), extended by QLoRA to 4-bit quantised bases (Dettmers et al., 2023), whose authors report near-full-fine-tuning quality from adapters trained on a single device. What the PEFT literature under-reports, and Chapter 7 documents concretely, is the fragility of these methods on very small corpora: with 43 training examples, one epoch separated the best model from an over-fitted one.

Evaluation practice in the generation literature leans on execution-based benchmarks descended from HumanEval (Chen et al., 2021), on coverage, or increasingly on LLM-as-judge protocols, for which Zheng et al. (2023) report high agreement with human preferences while cataloguing position, verbosity and self-enhancement biases. This project's evaluation design accepted their argument in both directions: a judge model was specified from a family disjoint from all candidates to avoid self-preference, and — when the judge component was not executed — the affected dimensions were dropped rather than approximated, leaving deterministic metrics whose provenance is checkable. For usability measurement the standard instrument remains the System Usability Scale (Brooke, 1996); it was included in the designed framework but no participant study was conducted, and no satisfaction results are claimed.

## 2.7 Synthesis and gap

Across these strands, three consistent lessons emerge. First, model output is unreliable in proportion to its distance from checkable evidence: unit-test generators succeed when the compiler pushes back (Schäfer et al., 2024), and web-form generators fail when nothing ties the model to the page (Li et al., 2026). Second, loops beat single shots: error-feedback repair, ranking and validity filtering recur in every successful system (Schäfer et al., 2024; Kang, Yoon and Yoo, 2023; Bouzenia, Devanbu and Pradel, 2025). Third, evaluation is fragmenting into deterministic and judgement-based strands whose disagreement is itself informative (Zheng et al., 2023).

What the literature does not offer is a system that joins these lessons end to end for quality assurance: requirement documents in; grounded, gated generation of UI, API and regression suites; versioned human approval at every irreversible step; live, replayable execution; outcome-transition regression gating in CI; and an evaluation regime — including fine-tuning of local models — whose every reported number is traceable to a raw artefact. That composite is the gap this project addressed, and RQ1–RQ3 operationalise it: what evidence the agent must consume (RQ1), why deterministic measurement must arbitrate quality (RQ2), and how the integration is achieved with production tooling (RQ3).
