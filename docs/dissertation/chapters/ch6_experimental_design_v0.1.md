# Chapter 6 — Experimental Design and Data Collection

## 6.1 Overview

Three experiments were designed to answer the research questions: a comparative evaluation of pre-trained local models (E1), a fine-tuning study with before-and-after measurement (E2), and a system-level validation of the end-to-end workflow (E3). ## 6.2 Experiment E1 — comparison of pre-trained models

**Design.** Three locally hosted pre-trained models were registered for comparison: `qwen2.5:latest` (the platform default), `qwen2.5-coder:latest` (code-specialised) and `deepseek-r1:8b` (reasoning-oriented). Each model was exercised on three pipeline tasks — test-plan generation, test-case generation and automation-code generation — over a benchmark of six fixed requirement items with acceptance criteria, coverage checklists and, for two items, reference test cases enabling the automation task. Sampling temperature was fixed at 0.1 for all models, repetitions were configured (three per cell, with per-model caps), and models were injected into the production agents non-invasively so that prompts and parsing were identical to deployment. Metrics comprised deterministic accuracy (reusing the platform's validation gates), completeness, requirement coverage, hallucination cleanliness, consistency across repetitions (structural, semantic and coverage-stability components), executability at the build-and-collection level, code quality, reliability and latency, aggregated under a pre-registered rubric. An LLM judge (`qwen3.5:397b-cloud`, deliberately disjoint from the candidates to avoid self-preference) was designed for qualitative dimensions but was not executed; judge-weighted dimensions were therefore dropped and the rubric renormalised.

**Data collection.** All runs were recorded in a SQLite store (59 runs across three batches, 25 July 2026), capturing latency, token counts, retries, status and per-metric values. For this dissertation the store was exported with the framework's own export tool into per-batch tables (one row per run, plus model and model-task roll-ups), preserved at `docs/dissertation/data/e1_export/` and reproduced in Appendix B. Two limitations of the collected data were recorded at design time rather than discovered post hoc: the raw generation texts referenced by the store were not preserved, and `deepseek-r1:8b` completed only two test-plan runs before being curtailed for slowness, so the three-model comparison is complete for latency and accuracy on that task only.

## 6.3 Experiment E2 — fine-tuning study

**Design.** Two models were adapted for the platform's two LLM-intensive roles: a planner (base `Qwen2.5-7B-Instruct`) and a coder (base `Qwen2.5-Coder-7B-Instruct`), using QLoRA on 4-bit bases (rank 16, dropout 0.05, sixteen adapted layers, batch size 1, constant learning rate 5×10⁻⁵, five epochs, completion-only loss, seed 20260808). The corpus was fully synthetic and deterministic: twenty-four training features across seven fictional applications (planner: 54 training / 8 validation examples; coder: 43 / 6), with a three-feature application family (a helpdesk product) held out entirely for evaluation. Adapters were fused, converted to GGUF, quantised to Q4_K_M and registered in Ollama as `qwen2.5-qa:latest` and `qwen2.5-coder-qa:7b`, so that evaluation exercised the deployable artefacts rather than the training checkpoints.

**Measurement.** Base and fine-tuned models were compared end to end on the held-out application through the production agents, scoring structured-output success, case counts and categories, traceability, plan-section completeness, and for code: compilation, forbidden-construct cleanliness, import resolution, marker and traceability conventions, page-object emission and latency. Training telemetry (per-iteration training and validation loss, memory, throughput) was retained and is analysed in Chapter 7, where the validation-loss trajectory of the coder is examined explicitly. A complementary set of platform-level runs — per-model projects created in the deployed system against the demonstration application (login, administrator-creation and product-creation features) — was performed through the user interface; the database export substantiating these runs is pending [EVIDENCE REQUIRED: PostgreSQL export of the per-model projects]. In line with the evidence rule of Section 3.3, summary workbooks whose per-cell values could not be traced to raw artefacts were excluded from the results; the exclusion and its rationale are documented in the evidence register.

**Sample sizes.** The held-out evaluation provided one run per feature per model (three case-generation features, one plan, three code-generation features). No repetition or variance estimation was possible at these sizes, and no statistical significance is claimed anywhere in this dissertation; E2 is reported as a structured case study, not an inferential experiment.

## 6.4 Experiment E3 — system-level validation

**Design.** The end-to-end claim — documents in, governed executable suites out — was validated against the bundled demonstration SaaS application, whose twenty-one user stories served as requirements input and whose three seeded defects (an incorrect login error message, a duplicated item insertion and a silently ignored deletion), toggleable at run time, were designed as ground truth for defect detection. Validation covered: generation of user-interface, API and regression suites through the platform's approval workflow; execution with live telemetry, producing JUnit results and evidence bundles; regression comparison between a promoted baseline and candidate runs; and the continuous-integration design, in which five marker-selected suites and a regression gate were defined for GitHub Actions.

**Data collection.** Execution evidence was collected automatically by the platform: 107 run directories (105 JUnit reports with pytest logs, screenshots and traces) were retained from local executions between 1 and 15 August 2026, and a five-phase preflight verification log recorded service health, workspace integrity, both grounding sources and suite execution status on 15 August. The generated suites themselves (21 test modules with provenance manifests recording content hashes and generation timestamps) constitute inspectable artefacts and are sampled in Appendix F, including defective generations retained deliberately as evidence of the current limits of gated generation. Two E3 components remained unexecuted at the time of writing and are reported as such: no GitHub Actions run artefact was preserved [EVIDENCE REQUIRED: `gh run list` output or workflow screenshots from the repository owner], and the seeded-defect detection procedure — executing the approved suites with each defect flag enabled and recording which tests fail — was designed but not yet run. The latter is the single highest-value pending experiment, since it would convert the seeded defects from a design feature into a measured detection rate.

## 6.5 Data management

All primary data was stored within the project tree and is preserved as follows: the E1 store and its exports (tracked branch file and `docs/dissertation/data/`), fine-tuning datasets, configurations, training logs and checkpoints (local, scheduled for backup as sole copies), execution artefacts and logs (local), and the platform databases (a development SQLite file and the PostgreSQL volume pending export). Anonymisation obligations identified in the audit — employer references, a personal e-mail default and populated example environment files — apply to the repository, not to the collected experimental data, which contains no personal information; their remediation is tracked in the evidence register.
