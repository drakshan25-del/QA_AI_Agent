# Chapter 5 — Implementation

## 5.1 Agent implementation

Six language-model agents were implemented in the engine, one per pipeline responsibility: requirement analysis, test-plan generation, test-case generation, automation-code generation, failure analysis and report narration (apps/qa-engine/agents/). Each agent was stateless, bounded by a configurable retry budget, and — critically — constrained to structured output: every call used LangChain's `with_structured_output` against a Pydantic schema, so no agent ever parsed free text from the model. Even the report agent's prose narrative was wrapped in a validated schema. Prompts were versioned (`PROMPT_VERSION = "v1"`) and each carried an explicit security guard declaring delimited requirement text, test-case JSON and captured error output to be data rather than instructions.

The test-case agent illustrated the defensive style adopted throughout. Generated cases were normalised against invariants, near-duplicates were detected with a difflib similarity threshold of 0.85, and the retry loop kept the *largest* valid set produced across attempts rather than failing outright when the requested minimum was not reached — logging the shortfall instead of silently inventing cases (agents/test_case_agent.py).

## 5.2 Grounding the generation

Two grounding mechanisms were implemented to anchor code generation in observable fact rather than model recall — the design response to the hallucination problem examined in Chapter 2.

For user-interface generation, a page inspector fetched candidate pages over HTTP and distilled them, using the standard-library HTML parser, into an inventory of inputs, buttons, links, headings, test identifiers, selects and forms; candidate paths were derived from page-object constants and from path tokens found in the test cases themselves, constrained to the same origin, and pages behind authentication were retried once through a real login probe (agents/page_inspector.py). The resulting inventory was rendered into the prompt as the authoritative page structure. The approach was deliberately lightweight, but its principal limitation was recorded honestly: because no browser was involved, JavaScript-rendered single-page applications produced empty inventories, and generation for such targets silently fell back to an ungrounded mode.

For API generation, an inspector retrieved the target's OpenAPI specification and distilled it into endpoint records with payload encodings and field names; every `api_client` call in generated code was then required to match a documented method and path, so that invented endpoints were rejected and regenerated rather than executed (agents/api_inspector.py; docs/V2_CONTRACT.md §1.1).

## 5.3 Generation gates and the repair loop

Automation generation was wrapped in a retry loop containing twelve deterministic checks, applied to the actual generated bytes before the output left the agent: syntactic parsing, resolvable imports, existence of every referenced page-object method, existence of every literal locator on the observed page, existence of every page path on the live target, a ban on fixed waits, API-style enforcement for browser-free tests, endpoint and payload documentation checks, an element-kind action contract (for example, `fill` was permitted only on fillable input types), removal of files that would shadow framework modules, and path de-duplication (agents/automation_agent.py). On failure, the rejection text was fed back to the model as a correction message and the sampling temperature was escalated by 0.25 per attempt, capped at 0.9 — a repair loop that converted validation failures into training signal within the session.

Marker assignment was removed from the model entirely: the engine stamped every generated file with the `generated` marker and merged the deterministic marker set implied by the requested test type, which is what made the CI suite selection of Section 4.8 trustworthy.

## 5.4 The deterministic security gate

A second, independent validation layer inspected generated files after generation and before any execution (apps/qa-engine/tools/code_validation.py; app/services/validation.py). Static checks rejected forbidden modules (such as `subprocess` and `socket`), shell and deletion calls, dynamic-code builtins (`eval`, `exec`, `compile`, `getattr` and related reflection primitives, since string concatenation defeats name-based analysis), filesystem mutators on any receiver, write-mode file access outside three sandboxed roots, hard-coded secrets matched by pattern, domain literals outside the allow-list, banned locator styles and fixed sleeps. Aliased imports were resolved before matching, and a regular-expression fallback scanned files that failed to parse, so broken syntax could not smuggle a dangerous call past review.

The ordering of checks was itself a security property: because pytest collection imports the module under test — executing any module-level code — the collection check was run only after all static checks had passed, and only inside a throwaway temporary mirror. A runnable self-check asserting that a deliberately unsafe snippet was rejected, and a clean one accepted, was embedded in the validation service and is reproduced in Appendix E.

## 5.5 Execution and telemetry

The execution runner materialised approved files from the database into the engine workspace, refused paths that escaped the automation directory, and would overwrite only files it had itself written, as recorded by content hash in an ownership manifest — a guard added after a generated file had once clobbered the framework's instrumented base page (engine/service/execution.py). The pytest command was assembled from the run configuration (browser, headed mode, screenshot policy, tracing, video, retries, parallel workers), launched in its own process group, and terminated on timeout or cancellation with a SIGTERM followed, after a ten-second grace period, by SIGKILL to the whole group. Step telemetry flowed through the bounded, replayable event path described in Section 4.6, with values on secret-hinting fields redacted before emission. Results were parsed from JUnit XML into per-test outcomes, evidence files were collected into screenshots, traces and videos, and failure classification combined deterministic regular-expression heuristics with a model judgement into one of five categories, each of which a human could override with a recorded reason.

## 5.6 Backend orchestration

All long-running work was implemented as jobs: a controller persisted a job row and dispatched a worker without awaiting it, acknowledging within two seconds, while the worker reported progress, wrote replayable log lines, honoured cooperative cancellation at checkpoints, and raced a hard timeout (apps/backend/src/modules/jobs/). Execution runs passed through a serialised queue with a configurable concurrency cap, a watchdog that reclaimed stalled slots, and the metrics-derived terminal outcome noted in Section 4.4.

The Git integration was implemented as two distinct paths. A local commit path wrote approved artefacts into a per-project workspace and committed them to an `ai-tests/` branch without touching the network; a separate push path shallow-fetched the remote default branch, overlaid only the approved files, committed the difference and pushed without force, using a transient token-bearing URL that was never written to Git configuration and was redacted from every error message. Both paths resolved and contained every artefact path, and the push path additionally rejected any path segment named `.git` (apps/backend/src/modules/git/git.service.ts). CI dispatch called the GitHub Actions API directly and refused, rather than simulated, dispatch when the repository or token was unconfigured.

## 5.7 Frontend implementation

The frontend was implemented as twenty routed screens covering upload, segment preview, analysis, plan and case review, automation review with code, diff, validation, traceability and execution-plan tabs, approvals, live execution, reports, regression comparison and audit (apps/frontend/src/App.tsx). The live view was built around a pure reducer that ordered and de-duplicated events by sequence number, which made replay, reconnection gap-filling and out-of-order delivery testable without a socket; eight unit tests covered exactly these properties. Authentication kept the access token in module memory only, with a single-flight refresh replaying failed requests, and generated-code edits were protected by dirty-state navigation blocking. Test-type generation controls (UI or API, with an optional regression-suite flag) and the regression comparison page — run pickers, summary tiles and per-bucket tables of pytest node identifiers — completed the workflow surface.

## 5.8 The sample application and seeded defects

A self-contained FastAPI demonstration application was implemented as the system under test, with login, items, dashboard, administration and product features, an HTML interface carrying a stable selector contract, and a mirrored JSON API (apps/qa-engine/sample_app/). Twenty-one user stories across five epics served as the requirements input. Three defects were deliberately seeded behind environment flags — a wrong login error message, a duplicated item insertion and a silently ignored delete — re-read on every request so that experiments could toggle them without restarting; these constituted the designed ground truth for defect-detection measurement.

## 5.9 Fine-tuning implementation

The fine-tuning strand was implemented as a reproducible pipeline (apps/qa-engine/finetune/). A fully synthetic corpus was authored as twenty-seven feature specifications across eight fictional applications; gold labels for cases, plans and code were rendered deterministically from the same specifications, and training examples were produced through the *production* prompts, so that the training distribution matched the inference distribution. Hard validation gates aborted the build on any label that failed schema validation, compilation or the framework's traceability conventions. Two models were adapted with QLoRA on Apple-silicon MLX — rank 16, dropout 0.05, sixteen adapted layers, learning rate 5×10⁻⁵, five epochs, 0.303 % trainable parameters — and exported through GGUF conversion and Q4_K_M quantisation (14,526 MiB to 4,460 MiB) into Ollama as `qwen2.5-qa:latest` and `qwen2.5-coder-qa:7b`. Training telemetry, checkpoints and evaluation outputs were retained and are analysed in Chapter 7.

## 5.10 Branch-only extension: the UI Scanner

A substantial extension — a UI Scanner and locator library comprising some 26,000 added lines across backend modules, five entities, an engine matching agent and eleven frontend components — was implemented on a separate branch and was **not merged** into the mainline system. Its design generated locator candidates in a deterministic stability order, validated each against the live page in a real browser, resolved ambiguity through scoped locators rather than positional indices, invoked the model only as a fallback, and marked unresolved steps for human review instead of fabricating selectors. It is reported here as implemented but unintegrated work, and no mainline claim in this dissertation rests upon it.

## 5.11 Implementation limitations

Several limitations were recorded during the audit and are carried forward to Chapter 8: page scanning was HTML-only and therefore blind to client-rendered applications; the locator-existence gate verified only literal locator expressions and failed open on dynamic ones; the engine's event history and idempotency cache were process-local and unbounded execution concurrency was possible at the engine level; and the generated suites themselves contained instructive defects — including a file with hard-coded credentials and sixty-second fixed waits that evaded the sleep and secret gates, and a file whose tests always skipped, masking two genuine errors. These are treated in Chapter 7 not as embarrassments but as primary evidence about the current limits of gated generation.
