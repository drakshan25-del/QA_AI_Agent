# Chapter 8 — Discussion and Evaluation

## 8.1 Answering the research questions

**RQ1 — What input artefacts are required?** The evidence supports a layered answer. Requirement artefacts (user stories, specifications, API documentation) were necessary but not sufficient: they drove analysis, planning and case generation, yet automation quality depended decisively on *observational* artefacts gathered at generation time — the distilled live page inventory and the parsed OpenAPI surface. When grounding was available, the deep-metric evaluation recorded fully clean hallucination scores for both models on automation; when grounding was absent by construction (client-rendered pages), generation silently lost its anchor, and the retained generated defects show what ungrounded or weakly checked output looks like. Execution logs completed the loop as the input to failure classification, regression comparison and retry feedback. The practical formulation is that a useful QA agent consumes three artefact classes — declared intent (requirements), observed reality (page and API surfaces) and measured history (execution outcomes) — and the system's usefulness degraded whenever one of the three was missing.

**RQ2 — Why measurable metrics rather than human judgement alone?** The fine-tuning study furnished the sharpest possible answer. On informal inspection, and on a narrow held-out slice, the fine-tuned coder appeared improved — perfect marker adherence, page-object emission, more compiling files. Deployed behind deterministic gates, it hallucinated page-object methods and produced unparseable files often enough to exhaust the retry budget, and the project itself reverted the default to the base model. The divergence was only *visible* because the pipeline measured rejection: a reviewer watching demonstrations would have seen the successes, not the rejection rate. The training telemetry then explained the mechanism — a validation-loss minimum at one epoch, after which the exported checkpoint over-fitted 43 examples — turning an anecdote into an evidenced failure mode consistent with the small-corpus fragility under-reported in the PEFT literature (Hu et al., 2022; Dettmers et al., 2023). The same lesson recurred in reverse during the audit of this dissertation's own inputs: summary workbooks whose cells could not be traced to raw artefacts were excluded, because measurement that cannot be audited inherits the weaknesses of judgement while wearing the costume of data.

**RQ3 — How can the agent integrate with production tooling?** The integration was demonstrated, with one honest boundary. Playwright integration was achieved through generated page-object tests executed by pytest with step-level telemetry; API integration through a guarded HTTP client whose every call was validated against the documented surface; regression through outcome-transition comparison against a promoted baseline; and CI through a marker-selected five-suite GitHub Actions design with a regression gate. The boundary is that hosted CI execution remained unevidenced at the time of writing, so RQ3 is answered fully at the design and local-execution levels and provisionally at the hosted level. The integration lesson mirrors Yang et al. (2024): most of the engineering effort lay not in prompting but in the interfaces — marker algebra, materialisation guards, event ordering — that made model output consumable by deterministic tools.

## 8.2 Findings in the context of the literature

The results align with, and in places extend, the reviewed work. The finding that the general 7B model outperformed its code-specialised sibling overall (0.783 against 0.733) — because test-*case* generation, a natural-language task, dominated the workload — refines the assumption implicit in code-model benchmarks that coding ability is the operative capability for test generation (Hui et al., 2024; Chen et al., 2021). The unsuitability of the reasoning model on latency (121 s per plan) quantifies, for this domain, the deliberation cost reported for R1-style models (Guo et al., 2025). The gate-miss examples — fixed waits and hard-coded credentials that evaded pattern-based checks — echo Schäfer et al.'s (2024) observation that validation, not generation, is the binding constraint, and support this project's defence-in-depth position over any single gate. Finally, the governance-first architecture occupies a position the agentic literature leaves open: where SWE-agent and RepairAgent maximise autonomy within an episode, this system demonstrates the cost and the value of withholding it — every irreversible action carried an auditable human decision, at the price of workflow latency that a fully autonomous design would not pay.

## 8.3 Threats to validity

**Internal validity.** E2's held-out evaluation had one run per cell; no variance is known, and single runs of stochastic systems can mislead — a risk partially mitigated by triangulation with training telemetry and operational evidence, which pointed the same way. The E1 judge component never ran, so qualitative dimensions were unmeasured and the rubric was renormalised; results are therefore deterministic-metric comparisons only. The evaluation-era "satisfaction" entries were a single researcher's informal ratings and were excluded from results.

**External validity.** All system-level evidence derives from one purpose-built demonstration application with stable, accessibility-friendly markup; generalisation to arbitrary SaaS products — particularly client-rendered applications, which the HTML-only page inspector cannot see — is not established. Model findings are bounded to 7–8B locally hosted models at temperature 0.1; cloud-scale models were supported by the platform but not systematically compared.

**Construct validity.** Deterministic accuracy, completeness and executability are proxies for test *usefulness*; the designed seeded-defect detection experiment, which would measure usefulness directly, remained unexecuted, and coverage of requirements is measured by token overlap rather than semantic entailment.

**Reliability and reproducibility.** The fine-tuning strand is strongly reproducible — seeded, deterministic corpus construction and preserved configurations — while E1 is only partially so: the run store survives, but the raw generation texts it references were not preserved, so its metrics can be re-audited but its outputs cannot be re-read. The two evaluation strands were never joined; no rubric-comparable before/after score exists for the fine-tuned models.

**Researcher bias.** Design, implementation and evaluation were performed by the same person. The mitigations were structural: metrics computed by code rather than opinion, raw artefacts retained where possible, and an explicit rule that untraceable numbers were excluded from this dissertation.

## 8.4 Ethical reflection

The project's ethical posture — synthetic and self-authored data, no participants, local inference keeping documents on-premises — held in substance, with two audit-identified deviations addressed rather than concealed: employer-named material used incidentally during development was excluded and scheduled for anonymisation, and committed example configuration files containing realistic-looking secrets were flagged for rotation and reduction to placeholders. A forward-looking consideration is recorded for practice: a system that generates and executes tests against live targets concentrates capability that could probe systems its operator does not own; the domain allow-list defaulting to localhost, the SSRF checking designed in the scanner branch, and the human approval gates are the implemented answers, and any deployment beyond a demonstration context would need them strengthened, not relaxed.
